= Установка Cuckoo Sandbox (KVM)


Проверенная процедура для лаборатории на **Ubuntu 18.04 LTS (bionic)** с **KVM/libvirt** (не VirtualBox).
Официальная книга Cuckoo 2.0.7 дополнена обходами для bionic и Win10 x64.

Ошибки и отладка — xref:utm/cuckoo-sandbox/troubleshooting.adoc#kvm-troubleshooting[раздел устранения неисправностей KVM].

== Что получится в итоге

* Host Ubuntu с Cuckoo **2.0.7** в Python 2.7 virtualenv
* Очередь задач в **PostgreSQL**, отчёты Web UI в **MongoDB**
* Гостевая **Windows 10 x64 LTSC** (build 19044) в KVM, снапшот `clean`
* Сеть libvirt `virbr0` (`192.168.122.0/24`), guest `192.168.122.105`
* Опционально: **Volatility 2.x** для RAM; **InetSim** — настраивается перед запуском Cuckoo (<<inetsim-setup>>)

== Два пользователя на host

[cols="1,2,3",options="header"]
|===
| Пользователь | Роль | Примеры команд
| `ваш_пользователь` | sudo, apt, `/etc` | `apt install`, `sysctl`, `cuckoo rooter`
| `cuckoo` | venv, Cuckoo, virsh | `pip install`, `cuckoo`, `cuckoo web`, `virsh`
|===

`ваш_пользователь` — ваш обычный аккаунт Ubuntu с **sudo** (в командах и путях подставьте свой логин).

Пользователя `cuckoo` **не добавляют в sudoers**.

=== Как читать блоки команд

Перед командами указано, **кто выполняет** и нужен ли **virtualenv** (`~/venv`):

[cols="1,3",options="header"]
|===
| Метка | Смысл
| **`ваш_пользователь`, sudo** | ваш пользователь с правами sudo; `apt`, правки `/etc`, `cuckoo rooter`
| **`ваш_пользователь`, без sudo** | проверки на host без sudo (или если уже в группе `libvirt`)
| **`cuckoo`, venv** | `sudo su - cuckoo` → `source ~/venv/bin/activate` — все `pip`, `cuckoo`, `cuckoo web`
| **`cuckoo`, без venv** | сессия `cuckoo`, venv не активирован (`virsh`, `groups`, `ulimit`)
| **guest Win10** | действия внутри гостевой Windows (GUI / cmd)
|===

Если venv нужен, в блоке есть строка `source ~/venv/bin/activate` — её выполняют **в той же сессии** перед `pip` / `cuckoo`.

== Пользователь cuckoo и лимиты

**→ `ваш_пользователь`, sudo**

[source,shell]
----
sudo adduser cuckoo
sudo usermod -a -G libvirt,kvm cuckoo
----

На bionic группа **`libvirt`**, не `libvirtd`. Группу **`pcap`** добавляют ниже — в блоке tcpdump (она создаётся командой `groupadd` только там).

=== Лимит открытых файлов (nofile)

Cuckoo при анализе держит много открытых дескрипторов (логи, PCAP, сокеты к VM, MongoDB).
На Ubuntu по умолчанию лимит часто **1024** — этого мало; без повышения возможна ошибка
*Too many open files*.

**Один раз** от `ваш_пользователь` откройте `/etc/security/limits.conf` и **в конец файла**
добавьте две строки (не заменяя существующие записи):

**→ `ваш_пользователь`, sudo**

[source,shell]
----
sudo nano /etc/security/limits.conf
----

[source]
----
cuckoo soft nofile 4096
cuckoo hard nofile 8192
----

* `soft` — рабочий лимит для новых сессий пользователя `cuckoo`
* `hard` — потолок, выше которого процесс сам поднять лимит не может

После сохранения файла **обязательно новый вход** под `cuckoo` (старые SSH/su-сессии
лимит не подхватят):

**→ `ваш_пользователь`, sudo** (переход в `cuckoo`) **→ `cuckoo`, без venv**

[source,shell]
----
# выйти из текущей сессии cuckoo и зайти снова, например:
sudo su - cuckoo
ulimit -n
----

Ожидаемо: **4096**. Если снова **1024** — проверьте опечатку в имени `cuckoo` в
`limits.conf` или что перелогинились именно пользователя `cuckoo`.

=== tcpdump без root для cuckoo

**→ `ваш_пользователь`, sudo** (первые четыре команды); **`getcap`** — без sudo

[source,shell]
----
sudo groupadd pcap 2>/dev/null || true
sudo usermod -a -G pcap cuckoo
sudo chgrp pcap /usr/sbin/tcpdump
sudo setcap cap_net_raw,cap_net_admin=eip /usr/sbin/tcpdump
getcap /usr/sbin/tcpdump
# ожидаемо: /usr/sbin/tcpdump = cap_net_admin,cap_net_raw+eip
----

После `usermod` — новый вход под `cuckoo` и проверка групп:

**→ `ваш_пользователь`, sudo** → **`cuckoo`, без venv**

[source,shell]
----
sudo su - cuckoo
groups
# ожидаемо: cuckoo kvm libvirt pcap
----

== PostgreSQL для очереди задач

=== PostgreSQL (host)

**→ `ваш_пользователь`, sudo** (`sudo -u postgres`)

Замените `ЗАМЕНИ_ПАРОЛЬ` на свой пароль. **`CREATE DATABASE` — одной строкой** (без `\` в конце:
в heredoc `<<'EOF'` обратный слэш не склеивает строки, а `psql` воспринимает `\` как служебную команду → `invalid command \`).

[source,shell]
----
sudo -u postgres psql <<'EOF'
CREATE USER cuckoo WITH PASSWORD 'ЗАМЕНИ_ПАРОЛЬ';
CREATE DATABASE cuckoo ENCODING 'UTF8' LC_COLLATE='en_US.UTF-8' LC_CTYPE='en_US.UTF-8' TEMPLATE template0 OWNER cuckoo;
GRANT ALL PRIVILEGES ON DATABASE cuckoo TO cuckoo;
\q
EOF
----

Ожидаемо по строкам: `CREATE ROLE`, `CREATE DATABASE`, `GRANT` — без `invalid command \`.

Проверка:

[source,shell]
----
psql -h localhost -U cuckoo -d cuckoo -c 'SELECT version();'
----

Ожидаемо: строка `PostgreSQL 10.23 ...` и `(1 row)`. Если экран с `(END)` и символами `~` — это **pager** (`less`), не ошибка: нажмите **`q`**, чтобы вернуться в shell.

Без pager (по желанию):

[source,shell]
----
PAGER=cat psql -h localhost -U cuckoo -d cuckoo -c 'SELECT version();'
----

image::utm/cuckoo-sandbox/kvm/A8-1-postgresql-create-db.png[Создание БД]

При ошибке `invalid command \` — xref:utm/cuckoo-sandbox/troubleshooting.adoc#postgresql-heredoc-backslash[troubleshooting]; часто `CREATE ROLE` / `CREATE DATABASE` / `GRANT` уже прошли.

=== connection, минимальный cuckoo.conf и схема БД

**→ `cuckoo`, без venv** (редактор) — `~/.cuckoo/conf/cuckoo.conf`

WARNING: После `cuckoo init` в конфиге по умолчанию **VirtualBox**: `machinery = virtualbox`, ResultServer **`192.168.56.1:2042`**. +
На **KVM + libvirt** (`virbr0`) этого адреса на host **нет**. +
Если добавить только `[database] connection` и сразу запустить `cuckoo`, получите: +
`Unable to bind ResultServer on 192.168.56.1:2042 ... Cannot assign requested address` — это **не** ошибка PostgreSQL, а **ещё не настроенный** Cuckoo под KVM. +
Guest VM на этом шаге **ещё не нужен**; нужно поправить **cuckoo.conf** (минимум ниже), затем первый запуск для создания таблиц в PostgreSQL.

**Минимум в `cuckoo.conf` перед первым `cuckoo`:**

[source,ini]
----
[cuckoo]
machinery = kvm
memory_dump = no
process_results = yes

[resultserver]
ip = 192.168.122.1
port = 2042

[database]
connection = postgresql://cuckoo:ВАШ_ПАРОЛЬ@localhost/cuckoo
----

* `192.168.122.1` — шлюз сети libvirt **default** (`virbr0`); интерфейс есть после установки KVM, **без** гостевой Windows.
* `kvm.conf`, `routing.conf`, `reporting.conf` — в следующем разделе; до первого `cuckoo` их можно не трогать.

Проверка, что адрес на host есть:

[source,shell]
----
ip addr show virbr0 | grep 192.168.122.1
----

**Не** `cuckoo migrate` на пустой БД — один раз запустите daemon (создаст таблицы через SQLAlchemy):

**→ `cuckoo`, venv**

[source,shell]
----
source ~/venv/bin/activate
cuckoo
# ожидаемо: «Waiting for analysis tasks» (Loaded 0 machines — норма, guest ещё нет)
# Ctrl+C
----

403 на `updates.json` при старте — **не критично** (версия 2.0.7).

Если **не** меняли `[resultserver]` — daemon не стартует (ошибка вверху терминала на скрине ниже). Сначала правка `cuckoo.conf`, затем снова `cuckoo`.

image::utm/cuckoo-sandbox/kvm/A8-1-cuckoo-resultserver-192-168-56-error.png[CRITICAL: 192.168.56.1 — до правки resultserver]

Подробнее — xref:utm/cuckoo-sandbox/troubleshooting.adoc#resultserver-bind[troubleshooting].

**→ `cuckoo`, venv** (или без venv — `psql` не требует venv)

Проверка PostgreSQL после успешного `cuckoo`:

[source,shell]
----
psql -h localhost -U cuckoo -d cuckoo -c '\dt'
psql -h localhost -U cuckoo -d cuckoo -c 'SELECT * FROM alembic_version;'
# cb1024e614b7
----

Ожидаемо: **10 таблиц** (`tasks`, `machines`, `samples`, …) и `version_num = cb1024e614b7`.
Красная ошибка `192.168.56.1` вверху скрина — **старый** неудачный запуск; ниже — успешная проверка БД.

== Конфигурация Cuckoo на host (полная)

**→ `cuckoo`, без venv**

Секции `[cuckoo]`, `[resultserver]`, `[database]` в `cuckoo.conf` вы уже задали перед первым запуском (PostgreSQL). Ниже — **проверить те же значения** и дописать остальные файлы; **`kvm.conf` с `[win10]`** — когда создадите guest (или заранее, но анализ заработает только после VM и snapshot).

=== kvm.conf

**→ `cuckoo`, без venv**

Файл: `~/.cuckoo/conf/kvm.conf`. После `cuckoo init` там шаблон с **`machines = cuckoo1`** и секцией **`[cuckoo1]`** — **замените на `win10`**: переименуйте секцию в **`[win10]`**, в `[kvm]` укажите `machines = win10`, в секции машины — `label = win10` (имя домена libvirt из virt-manager). ----

interface = virbr0
machines = win10

[win10]

platform = windows
ip = 192.168.122.105
snapshot = clean
osprofile = Win10x64_19041
----

== Гостевая Windows 10 в KVM

Guest — виртуальная машина **QEMU/KVM**. Имя домена **`win10`**, IP **`192.168.122.105`**, снапшот **`clean`** — те же значения, что в `kvm.conf`.

**→ `ваш_пользователь` или `cuckoo`** — virt-manager на host (нужны группы `libvirt`, `kvm` и **log out / log in**). Внутри guest все шаги — в консоли VM (Spice/VNC).

=== Порядок этапов (не перескакивать)

[cols="1,2,1",options="header"]
|===
| # | Этап | Где
| 1 | Создание VM в virt-manager | host, GUI
| 2 | Установщик Windows (Setup) | guest, синие экраны
| 3 | OOBE (первый вход) | guest
| 4 | Сеть: discoverable, закрыть Edge | guest
| 5 | Статический IP | guest
| 6 | Defender, UAC, firewall, ping host↔guest | guest + host
| 7 | Python, VC++, Pillow | guest
| 8 | Cuckoo Agent | host + guest
| 9 | Action Center, уведомления | guest
| 10 | Defender: реестр + Safe Mode | guest
| 11 | Снапшот `clean` | virt-manager + host
|===

Целевая сборка: **Windows 10 Enterprise LTSC 21H2**, build **19044.x** — проверка **`winver`** сразу после OOBE (<<win10-guest-verification>>).

=== Требования к guest

* **ОС:** Windows 10 **x64** (рекомендация Cuckoo 2.0+); в этой инструкции — **Enterprise LTSC** (build **19044.x**, проверка <<win10-guest-verification>>).
* **Диск:** **qcow2** (обязательно — иначе снапшоты KVM не работают).
* **Сеть:** сеть libvirt **`default`** → мост **`virbr0`**, подсеть **`192.168.122.0/24`**; у guest — **статический** IP (не DHCP).
* **UAC:** отключить после установки (Win7+).
* **Result Server** на host слушает **`192.168.122.1:2042`** — guest должен достучаться до `.1`.

Перед созданием VM проверьте сеть на host:

**→ `ваш_пользователь` или `cuckoo`, без venv**

[source,shell]
----
virsh net-list --all
ip addr show virbr0 | grep 192.168.122.1
----

Ожидаемо: сеть **`default`** в состоянии **active**; на **`virbr0`** адрес **`192.168.122.1/24`**.

=== Создание VM в virt-manager

==== Подготовка

1. ISO Windows 10 x64 LTSC — локальный файл (например `~/Downloads/Win10_LTSC.iso`).
2. Запустите **Virtual Machine Manager** (`virt-manager`). В списке слева должно быть **QEMU/KVM — Connect** без ошибки (скрин после log out — в разделе установки KVM).
3. Свободное место на host: диск guest **≥ 60 GB** (qcow2 растёт по мере заполнения).

==== Мастер «Create a new virtual machine»

**File → New Virtual Machine** (или значок «Create»):

[cols="1,3",options="header"]
|===
| Шаг мастера | Что выбрать
| 1. How would you like to install? | **Local install media (ISO image or CDROM)**
| 2. ISO | **Browse** → выбрать ISO Win10; если OS type не определился — **Windows 10**
| 3. Memory and CPU | **2048** MiB RAM, **2** CPUs (на host с 8 GiB не давать guest больше 2–4 GiB)
| 4. Enable storage | **Create a disk image**; размер **≥ 60 GB**; формат по умолчанию **qcow2**
| 5. Ready to install | Включить **Customize configuration before install** → **Finish**
|===

Откроется окно **Details** (настройка железа **до** первой загрузки с ISO). VM должна быть в статусе **Shutoff**.

==== Вкладка Overview (обзор)

**→ virt-manager → win10 → Details → Overview**

[cols="1,2,2",options="header"]
|===
| Поле | Значение | Зачем / `kvm.conf`
| Name | **`win10`** | **`label = win10`** — имя домена libvirt (`virsh list --all`)
| Architecture | **x86_64** | 64-bit guest
| Hypervisor | **KVM** | —
| Firmware | **BIOS** | для LTSC x64 на bionic достаточно BIOS + i440FX
| Chipset | **i440FX** | типичная пара с BIOS; не менять после установки
|===

*UEFI:* если в списке Firmware пункт **UEFI** — «Not found», пакет OVMF не установлен. Для этой лаборатории оставьте **BIOS**. UEFI опционален (`sudo apt install ovmf`); смена firmware **после** установки Windows рискованна — не трогать.

xref:utm/cuckoo-sandbox/troubleshooting.adoc#virt-manager-uefi[UEFI Not found — troubleshooting].

==== Вкладка SATA Disk 1 (диск)

**→ Details → SATA Disk 1**

[cols="1,2,2",options="header"]
|===
| Параметр | Значение | Примечание
| Source path | `/var/lib/libvirt/images/win10.qcow2` (или путь из мастера) |
| Storage format | **qcow2** |
| Disk bus | **SATA** | Windows видит диск без virtio-драйверов на этапе установки

=== Defender, UAC, firewall

**Где работать:** внутри **гостевой Windows** (окно VM в virt-manager). На Linux-host этот шаг не выполняется.

**Зачем:** **Defender** удаляет или блокирует тестовые файлы при анализе, **брандмауэр** не пускает связь с Linux-host, **UAC** показывает лишние окна при запуске программ в VM. Отключаем **до** установки Python и Cuckoo Agent (этапы 7 и 8). **Action Center** — отдельно, этап 9.

**Control Panel → User Accounts → Change User Account Control Settings** — **Never notify**.

*Альтернатива (оставить firewall включённым):* **Win+R** → `wf.msc` → **Inbound Rules** → включить **File and Printer Sharing (Echo Request - ICMPv4-In)** для профиля **Private** — тогда ping с host заработает без полного отключения firewall.

**→ guest Win10**. Agent должен слушать **:8000** после каждого входа в Windows **с правами администратора** (иначе analyzer предупреждает «not running as Administrator»). Ярлык в `shell:startup` прав **не** даёт — нужен **Task Scheduler**.

**Вкладка General (Общие)**

* **Security options:** **Run only when user is logged on**
* **User:** `ВАШ-HOSTNAME\cuckoo` (например `DESKTOP-ABC123\cuckoo`)

* **Configure for:** Windows 10

**Вкладка Triggers (Триггеры)** → **New…**

* **Begin the task:** **At log on** (не *At startup*)
* **Specific user:** `…\cuckoo`
* **Enabled** — ON
* При необходимости **Delay task for:** 30–60 s (если :8000 не сразу после входа)

**Вкладка Actions (Действия)** → **New…**

* **Action:** Start a program
* **Program/script:** `C:\Python27\pythonw.exe`
* **Add arguments:** `C:\Users\cuckoo\Desktop\agent.pyw`
* **Start in (optional):** `C:\Users\cuckoo\Desktop`

Путь к `agent.pyw` — **полный**; не обрезать до `koo\Desktop\…`.

**Вкладка Conditions (Условия)**

* Снять **Start the task only if the computer is on AC power** (для VM).
* Idle / Wake — не включать.

**Вкладка Settings (Параметры)**

* **Allow task to be run on demand** — ON
* **If the task is already running:** **Do not start a new instance**

**Обновление** после правок guest (в т.ч. Defender): удалить старый, создать новый (**без** `snapshot-revert`):

[source,shell]
----
virsh snapshot-delete win10 clean
virsh snapshot-create-as win10 clean --description "Clean baseline - Defender off"
----

[[inetsim-setup]]
== Установка и настройка InetSim

**→ host**, один раз **до** запуска Cuckoo и любых submit. InetSim подменяет DNS/HTTP для guest; для `route=inetsim` нужны также **rooter** (T0) и **IP forwarding**.

В `~/.cuckoo/conf/routing.conf` секция `[inetsim]` уже задана при полной конфигурации host (<<routing-inetsim-conf>>); здесь — установка службы и sysctl на host.

[[routing-inetsim-conf]]
**→ `cuckoo`, без venv** — проверить `routing.conf`:

[source,ini]
----
[routing]
route = none

[inetsim]
enabled = yes
server = 127.0.0.1
ports =
----

**→ `ваш_пользователь`, sudo** — модули, forwarding, пакет:

[source,shell]
----
sudo modprobe br_netfilter
echo br_netfilter | sudo tee /etc/modules-load.d/cuckoo-bridge.conf
sudo tee /etc/sysctl.d/99-cuckoo-bridge.conf << 'EOF'
net.bridge.bridge-nf-call-iptables = 1
net.bridge.bridge-nf-call-ip6tables = 1
net.ipv4.ip_forward = 1
net.ipv4.conf.all.route_localnet = 1
EOF
sudo sysctl --system
sudo apt-get install -y inetsim
----

**→ `ваш_пользователь`, sudo** — `/etc/inetsim/inetsim.conf` (синтаксис InetSim 1.2.7: **пробел**, не `=`). В файле эти строки по умолчанию **закомментированы** — снимите **`#`** в начале каждой строки (или добавьте параметры без `#`):

[source]
----
service_bind_address 127.0.0.1
dns_bind_port        53
dns_default_ip       192.168.122.1
----

[source,shell]
----
sudo systemctl enable inetsim
sudo systemctl restart inetsim
sudo systemctl status inetsim
dig @127.0.0.1 example.com +short
----

Ожидается: **`192.168.122.1`** (одна строка — фейковый IP InetSim для любого домена). InetSim в `systemctl` — **active**. На `192.168.122.1:53` может сидеть **dnsmasq** libvirt — проверку DNS делайте только через **`@127.0.0.1`**, не через `.1`.

image::utm/cuckoo-sandbox/kvm/A8-4-inetsim-conf-bind-dns.png[InetSim conf]
image::utm/cuckoo-sandbox/kvm/A8-4-routing-conf-inetsim.png[routing.conf]

Отладка — xref:utm/cuckoo-sandbox/troubleshooting.adoc#inetsim-not-working[InetSim troubleshooting].

== Запуск Cuckoo (каждая сессия)

Перед submit: **InetSim запущен** (`systemctl status inetsim`), guest из снапшота **`clean`**.

Четыре **отдельных терминала**:

[cols="1,1,2,2",options="header"]
|===
| T | Кто | Команда | Назначение
| T0 | **`ваш_пользователь`, sudo** | `sudo /home/cuckoo/venv/bin/cuckoo rooter -g cuckoo` | rooter (iptables для InetSim)
| T1 | **`cuckoo`, venv** | `cuckoo` | scheduler
| T2 | **`cuckoo`, venv** | `cuckoo web -H 0.0.0.0 -p 8080` | Web UI (**опционально**, GUI отчётов)
| T3 | **`cuckoo`, venv** | `cuckoo api -H 0.0.0.0 -p 8090` | REST API (**опционально**)
|===

**T0** — из-под **`ваш_пользователь`** (sudo), **не** из venv. Бинарник Cuckoo: **`/home/cuckoo/venv/bin/cuckoo`** (venv пользователя `cuckoo`). Не пишите `~/venv` — при sudo это будет `/home/ваш_пользователь/venv` и `command not found`.

**T1** (scheduler) — **обязателен** для любого анализа. **T2** (Web UI) — **опционально**, если нужно **просматривать результаты в браузере** (GUI); без T2 submit из терминала всё равно работает, отчёты лежат на диске в `~/.cuckoo/storage/`. **T3** (REST API) — **опционально**, если нужен submit/статус через HTTP API.

Минимум для lab с InetSim: **T0 + T1**. Добавляйте **T2** и/или **T3** по необходимости.

**T1** (и **T2** / **T3**, если запускаете) — Linux-пользователь **`cuckoo`**, virtualenv **`/home/cuckoo/venv`** (тот же, где ставили `cuckoo==2.0.7` в начале инструкции). **Не** venv от `ваш_пользователь` — у админа своего venv нет или он пустой.

В **каждом** нужном терминале (минимум **один** — T1; **T2** и **T3** — отдельные терминалы, по желанию):

1. Войти под **`cuckoo`** (если prompt показывает `ваш_пользователь@…`):

+
[source,shell]
----
sudo su - cuckoo
----

2. Активировать venv (**`~`** здесь = `/home/cuckoo`):

+
[source,shell]
----
source ~/venv/bin/activate
----

+
Ожидаемый prompt: **`(venv) cuckoo@hostname:~$`**.

3. Проверка (опционально):

+
[source,shell]
----
which cuckoo
# /home/cuckoo/venv/bin/cuckoo
----

4. Запустить команду из таблицы для этого терминала:

* **T1:** `cuckoo` — **обязательно**
* **T2:** `cuckoo web -H 0.0.0.0 -p 8080` — **опционально** (GUI отчётов в браузере)
* **T3:** `cuckoo api -H 0.0.0.0 -p 8090` — **опционально** (REST API)

Если `cuckoo: command not found` — venv не активирован (`source ~/venv/bin/activate`) или вы не под пользователем **`cuckoo`**.

[[submit-options]]
== Постановка задач на анализ (submit)

**→ `cuckoo`, venv** (T1 запущен; для `route=inetsim` — ещё **T0** и InetSim, см. <<inetsim-setup>>).

Базовый синтаксис:

[source,shell]
----
cuckoo submit --options "ключ=значение,..." /путь/к/файлу
cuckoo submit --package ПАКЕТ --options "..." http://url
----

Пакет (`--package`) Cuckoo часто подбирает сам по типу файла. Явно указывайте **`exe`**, **`ie`**, **`zip`**, **`dll`** и т.д., если автоопределение ошиблось. Полный список — `analyzer/windows/modules/packages/` в исходниках Cuckoo и link:https://cuckoo.readthedocs.io/en/latest/usage/packages.html[packages.rst].

=== Параметры `--options`

[cols="2,3",options="header"]
|===
| Параметр | Назначение
| `human=0` | Отключить модуль **Human** (эмуляция мыши, клики по кнопкам «Next», «OK»). Без него на Win10 analyzer может зациклиться на Action Center («No **new** notifications» содержит подстроку **new**). Для **GUI-сэмплов и малвари** в lab — **всегда** `human=0` (guest настраивается в <<win10-action-center>>).
| `free=yes` | Запуск **без** cuckoo-monitor: behavioral-логов API не будет, процесс «живёт сам». Только отладка GUI (например, виден ли диалог mspaint). **Не** используйте для анализа малвари — нужен monitor и дерево процессов.
| `route=inetsim` | Трафик guest через **InetSim** на host (фейковые DNS/HTTP). Меньше шума, чем NAT в интернет. Нужны **T0** (rooter), `enabled = yes` в `routing.conf` и `systemctl status inetsim` → active.
| `enforce_timeout=yes` | Анализ идёт **весь** timeout из `cuckoo.conf` (`[cuckoo]` → `analysis_timeout`), без досрочного завершения, когда все отслеживаемые процессы уже вышли. Полезно для URL/IE и долгих сценариев.
| `procmemdump=yes` | Дампы памяти **отслеживаемых** процессов (не полный снимок VM).
| `password=…`, `file=…` | Только пакет **`zip`**: пароль архива и имя файла внутри для запуска.
| `arguments=…` | Аргументы командной строки для **`exe`** / **`dll`** / **`zip`** (см. packages.rst).
|===

Отдельные флаги CLI (не в `--options`):

* **`--memory`** — полный дамп RAM guest после анализа (для Volatility, <<volatility-setup>>). Часто вместе с `free=yes`, чтобы хуки monitor не искажали память.
* **`--enforce-timeout`** — то же, что `enforce_timeout=yes` в options.
* **`--package ie`** — URL открывает **Internet Explorer** в guest (отдельный браузер не ставим).

=== Типичные сочетания

**Исполняемый файл (малварь, тестовый .exe):**

[source,shell]
----
cuckoo submit --options "human=0,route=inetsim" /path/to/sample.exe
----

`route=inetsim` опционален, если сеть не нужна — достаточно `human=0`.

**URL (InetSim + IE):**

[source,shell]
----
cuckoo submit --package ie \
  --options "human=0,route=inetsim,enforce_timeout=yes" \
  http://example.com
----

**ZIP с паролем:**

[source,shell]
----
cuckoo submit --package zip \
  --options "human=0,password=ПАРОЛЬ,file=payload.exe" \
  sample.zip
----

Статус задачи: `cuckoo status <id>`; отчёты — `~/.cuckoo/storage/analyses/<id>/` или Web UI (**T2**). Ошибки submit/анализа — xref:utm/cuckoo-sandbox/troubleshooting.adoc[Troubleshooting].
